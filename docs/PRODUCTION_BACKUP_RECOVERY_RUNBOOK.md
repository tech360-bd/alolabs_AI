# Backup verification and isolated recovery

**Scope:** a logical database dump plus supported local file storage, including its ownership metadata. The backup is not an encrypted offsite copy, signed provenance, consistent transaction across SQL and files, snapshot of external object storage or proof of application recovery. `restore_tested:false` is intentional. Keep `deploy/scripts/restore.sh` blocked against production.

1. Have an authorized operator confirm database engine, expected database name, real storage mapping, secure access and free capacity. Use Node 22.13+, Python 3 and SQLite online backup support or a compatible `mysqldump`. MySQL credentials come from the private deployment environment, percent encoded in the URL. Do not paste URLs into command lines or enable shell tracing. Unsupported connection options fail rather than being silently ignored. Validate host-specific TLS and client configuration with the DBA on staging first.
2. Verify SSH trust and the reviewed backup bundle on the control host. Preflight and backup must both succeed. Capture the `BACKUP_VERIFIED` path and run status, not environment values. Only timestamp-plus-random-suffix directories are published recovery points. Never count `.stage-*` or treat an incomplete staging directory as a completed backup. After an interruption leave remnants alone until an authorized operator establishes that no writer holds them.
3. On an **isolated copy**, use `bash deploy/scripts/verify-backup-checksums.sh "$snapshot"`. Check a single expected database artifact, manifest/commit agreement, storage flags, checksum coverage and archive contents. New snapshots checksum the manifest too. Protect a separately authenticated offsite copy of the checksums; a writer able to replace the whole snapshot can recompute hashes. Reject suspicious names, links or devices before extraction into a private empty directory. Never extract into an application checkout.
4. For SQLite, open a copy of `database.sqlite` read-only, run `PRAGMA integrity_check` and verify known records. For MySQL/MariaDB, provision a **new empty disposable database on a separate isolated service**, using an account restricted to that target, no production network/credentials and a compatible client. Check gzip integrity; import the decompressed stream only into that reviewed target. Do not replay an untrusted dump with elevated privileges. Compare schema, row counts and known values, then run the application against the isolated copy. See `tests/reliability/mysql-restore.sh` for the loopback CI fixture, not an operator production command.
5. Restore archived storage into temporary paths; compare file bytes, ownership metadata and tenant access (owner allowed, another tenant denied). Independently restore/version-check external providers. Record snapshot ID, SHA, restored target, timing, checks and approver. Keep any evidence free of personal data and secrets. Only a separate incident/change approval can authorize a production recovery plan.
6. Retention serializes verification and publication on a local POSIX filesystem, keeps at least 14 verified sets and only prunes older eligible sets. Invalid, legacy and staging directories do not count and are **not automatically deleted**. Verify disk headroom: checksumming retained snapshots costs I/O. Do not assume equivalent locking or rename guarantees on network mounts. Alert on missed schedules, growing invalid sets, storage exclusions and failed restore drills. Do not prune manually to make a failed verification green.
