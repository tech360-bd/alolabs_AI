# Release activation and rollback — operator approval required

This is a runbook, not evidence of a live rollout. The application is a single PM2 fork (`alolabs-agentos`), not a zero-downtime cluster. A short interruption is expected during process registration. Caddy still targets loopback:3011. Queue/realtime services are not part of the PM2 switch. No production steps were executed during remediation.

## Before first use

1. Check the PR's actual MySQL build/start, database restore, browser and security checks. Rehearse with the same Bun, Node, PM2, database privileges, volume mounts and supervisor account on **staging**. Require two reviewers for the first cutover. Do not use a green SQLite test as a production readiness decision.
2. Enroll the verified server pin ([rotation runbook](SSH_HOST_KEY_ROTATION_RUNBOOK.md)). Restrict the `production` environment to main, require reviewers and disable review bypass. Approve the exact full SHA shown on the dispatch. Re-running the same run keeps its SHA. A new SHA needs a new dispatch and approval. Before any production connection the workflow requires the latest CI, MySQL, backup portability and security runs on that exact main SHA to have succeeded. For a path-filtered workflow without a push run, request the relevant test workflow on main and confirm its head SHA; never skip this gate.
3. Inventory `APP_DIR`, checkout owner, `origin`, sudoers, PM2 home/owner, boot-time saved process list, file access, free space and DB status. Verify `flock`, Git, Linux procfs, `ss`, Python 3, Bun 1.3.4, Node 22.13+ and mysql client tools. Never grant blanket sudo to resolve a failed preflight.
4. The control checkout stays put. Install the approved backup script **and its reviewed helpers** in the control checkout under a separate approved host-change procedure, without replacing running artifacts, secrets or data. The scheduled job refuses to run mismatched code. Monitor the next backup; enrollment or hash drift can stop scheduled backups.
5. Identify the live physical storage before provisioning anything: `storage`, `uploads`, `public/uploads`, `data`, custom storage and object stores. Verify these locations, permissions and captured ACL metadata with a restore. A conflicting standalone directory or custom relative mapping blocks the switch; do not resolve by deleting files. Use canonical shared paths and independently back up remote storage. Check existing `.env.production`, `.env.config` or `.env` is private, not tracked, and agrees with the running process; **never print it**.

## During a reviewed deployment

`deploy/scripts/deploy.sh` takes an exclusive lock at `APP_DIR/.alo-releases/lock`. The workflow verifies main ancestry and the GitHub origin, not merely a branch name. It preserves the legacy checkout as the initial rollback target. New builds use unique detached clones in `.alo-releases/releases`. The control checkout's branch and the old release's dependencies/build are not reset. `current` is a same-filesystem symlink changed with a rename.

A deployment must pass its backup, database, schema, build and artifact checks. With Prisma-format migrations, **approval alone is insufficient**: recorded checksums must match, and pending statements must match the narrow nullable-column allowlist. Other DDL needs a separate reviewed expand-and-contract plan. Migration effects persist on code rollback; use a DBA, never a database reset. A failed migration can be partially applied; inspect actual history before retrying.

At activation the script records `activation-pending` (previous directory, candidate directory, run ID), switches the pointer and re-registers **only** the named process using the retained ecosystem config. Ordinary fork-mode `startOrReload` alone can reuse the old absolute entrypoint. The script checks actual PID, cwd (release or its standalone tree), interpreter, loopback listener, unchanged database target and HTTP readiness. History includes UTC time, run, approved/previous/active SHA and outcome. Do not infer success from a changed symlink alone.

## Failure or interrupted activation

- **Before activation:** inspect the failed gate. The old process and artifacts remain. Preserve candidate and journal for diagnosis. Fix, review and retry. Nothing automatically prunes releases.
- **After activation:** the EXIT handler re-points to the previous release, starts it from its retained config and checks readiness. Check `history` for `rolled_back`, not just the workflow exit status. Confirm a real request succeeds. The isolated PM2 test also restarts the recovered process; do not restart production merely to repeat that test.
- **Power loss, SIGKILL or `rollback_failed`:** stop further jobs. Do not remove the lock file or clear `activation-pending` to force a retry. Through a verified console, obtain an incident lead's approval and the same kernel lock. Read pointer, pending record and history, check `pm2 pid alolabs-agentos`, `readlink -f /proc/<pid>/cwd`, `ss -lntp` and `/api/health/ready`; do not dump process environment. Identify the retained previous directory by its SHA, check the saved `ecosystem.config.js`, server artifact, shared storage and DB compatibility. Only then atomically restore `current` with the reviewed `switch_release` helper and re-register just that PM2 app from the previous ecosystem config as the established supervisor owner. Verify the actual listener PID, cwd, interpreter, database target (compare privately), HTTP response and an authenticated smoke test. Archive evidence, append a manual recovery record and retire the pending marker only after verification. If previous code cannot serve against the schema, escalate to the DBA and roll forward; **do not import a backup over the live DB**.
- **After success:** operator verifies boot/resurrection separately before persisting any process-manager state; avoid overwriting unrelated PM2 registrations. Monitor errors and backups and reserve disk space for retained releases. Do not use the legacy systemd rollback scripts or rebuild in the active directory.
